# 如何判斷模型有沒有用

2026-11-10文件整併：資料、特徵與驗證舊計畫已合併至此。當前唯一資料版本是small-api-v9，1098筆（train702／test150／validation150／challenge96），離線生成，沒有宣稱全部HTTP執行。舊計畫的TF-IDF比較、三平台輪流留一與三平台重訓沒有實作，不當成目前成果。

目前train／test為Bagisto＋Shopware，validation為Sylius結合httpParamsDataset payload，challenge另測保留語境；Medusa只做展示，不入訓練、選特徵或調門檻。normal、sqli、xss描述請求意圖，不以HTTP狀態或攻擊成功決定。正常樣本應涵蓋特殊字元、技術文字及非攻擊錯誤，不能只用容易的購物短句。

一筆是完整請求；method、path、query、headers與body採共用request_input處理，遮蔽憑證實值後，依feature v6產生數值與原始字元2～5gram固定hash特徵，共2402維。沒有擬合TF-IDF詞彙表，原始請求不正規化；分組用的保守骨架分析視圖不作模型輸入。明確平台名稱、情境名稱、標籤與response不作推論特徵，但路徑仍可能帶有平台偏差，不能因此宣稱已消除平台識別。

同session／來源、對照配對、重複與近似骨架先分組再切分，不能只換ID或數字當新考題。provenance、skeleton-catalog與語義／語言／地址規則保留，用來發現跨集合關聯、內容指紋改動或不合理normal值；不能證明地址可投遞、API業務成功或攻擊有效。未解析的格式及模型錯誤要如實記錄，沒有契約不等於攻擊。

早期只擴充train、保留測試CSV不變的做法是歷史階段；v9後來明確修正正常背景值，歷史v5／v6分數不能當作v9分數。現用報告在results/colab-v9-2026-11-09，當前資料／程式見README。模型工具41項測試及Colab ZIP完整性檢查通過，測試通過不代替研究效果證據。


目前程式以固定參數訓練，分開輸出 test 與獨立 validation。輸出完整清單、Colab 與跨系統自我檢查見 model/README.md。

分數是證據的一部分，不是萬用的有效證明。結論只涵蓋實際測過的平台、資料、請求格式與攻擊範圍。未實測候選的試跑報告不能當正式效果；不再以人工核准作為訓練條件。

## 先訂規則，再看考試結果

1. 保留標籤來源與判定依據，不設人工核准門檻。攻擊標籤描述請求意圖，不由 HTTP 200／500 決定，也不代表攻擊成功。
2. 先固定測試平台、採集範圍、特徵、模型比較方式及指標。相同 session、對照配對、來源重複群不能跨集合；目前依原文重算保守骨架及來源關聯，但不保證辨識所有語意等價變體。
3. 只用 train 內的分組驗證改特徵、參數與門檻。test 與 Sylius 獨立 validation 都是保留評估集，不參與選模型。只因測試分數不好而反覆改版，就等於用考題練習。
4. 開發完成後，對新的、事前保留的採集批次測試。當前已有Colab v9離線報告，但反覆查看同一保留集合後再改版，該集合便不再是完全未見考題；正式結論仍需事前保留的新批次。
5. 保留所有實驗，不能只挑最高分。程式拒絕覆蓋非空輸出目錄；但不能自動阻止人工反覆使用同一測試集。

## 報告裡的指標

| 指標 | 白話意義 | 判讀重點 |
|---|---|---|
| Accuracy | 全部請求有多少猜對 | normal 很多時可能看似很高 |
| 各類 Precision | 說是這一類的請求，有多少真的對 | 攻擊 precision 低會產生很多假警報 |
| 各類 Recall | 真的是這一類，有多少被找出來 | SQLi／XSS 分別報，不能互相掩蓋 |
| 各類 F1 | Precision 與 Recall 的折衷 | 不等於誤報成本或網站可用性 |
| Macro-F1 | 三類 F1 等權平均 | 主指標之一，避免 normal 數量壓過攻擊 |
| Balanced accuracy | 三類 Recall 等權平均 | 補充觀察少數類別 |
| 正常誤報率 FPR | 正常請求被判攻擊的比例 | Demo 正常流程的優先指標，越低越好 |
| 攻擊偵測 Recall | 所有攻擊中，有多少未被當成正常 | SQLi 誤判成 XSS 在這裡仍算有抓到；三類指標仍會扣分 |
| 攻擊漏報率 | 攻擊被當成正常的比例 | 不可為了零誤報就把所有請求都判 normal |
| 混淆矩陣 | 每一類被判到哪一類，各有幾筆 | 列是真實、欄是預測，顯示實際筆數 |
| ROC-AUC | 機率排序能否分開該類與其他類 | 高 AUC 不保證實際告警門檻夠好 |
| Average Precision | Precision-Recall 曲線的摘要 | 受類別比例影響，應一起看 prevalence；不混稱梯形 PR-AUC |
| 群組重抽樣區間 | 換一批獨立群組時分數可能有多不穩 | 群組少於 20 時不報；20 組也不保證資料足夠 |
| 本機 median／p95 延遲 | 特徵擷取加單筆預測花多久 | 不含網路、模型載入及真實服務負載 |

## 不只跟自己比

程式已比較「永遠猜訓練集最多的類別」。若輸給它，模型連基本價值都不足；贏過它也不等於 XGBoost 最佳。

正式研究建議再加入簡單詞法規則與 Logistic Regression，在同一切分、同一特徵與相同調參預算下比較；規則也必須先固定，不能針對測試 payload 加特例。可加移除詞法規則特徵的消融實驗，判斷 XGBoost 是否只記住容易的關鍵字。這些比較目前尚未實作。

## Demo 優先：正常網站要能用

使用者目前優先考量正常流程順暢。第一階段建議只記錄與告警，不將模型預測接成自動封鎖；模型異常或逾時也不應讓網站請求失敗。這是建議的整合方式，目前訓練／推論 CLI 沒有修改網站或實作攔截器。

若之後需要攔截：先在 validation 設定可接受的正常誤報上限，再在此前提下提高攻擊偵測 Recall。沒有滿足限制的門檻就維持告警模式，不在 test 上挑一個最好看的門檻。可接受上限與攻擊 Recall 下限尚待依實際用途決定，目前不自動判定『合格』。

另外需要獨立的正常流程驗收：登入、瀏覽商品、搜尋、購物車、結帳測試，以及合法特殊字元、錯誤密碼、無效參數等正常／非攻擊錯誤。分別記錄誤報筆數與總數。即使測試 100 筆完全零誤報，也不能宣稱實際誤報率必為零。

## 可以支持的結論與仍缺的證據

同一個模型可在指定保留平台評估跨平台能力。新採集批次可補充時間／採集差異的證據；需要未見家族能力時再另外保留家族，不能拿跨平台分數代替。

目前可追溯的是 195 筆歷史 normal 請求及尚未實測的情境／header 計畫。先前「260 筆、10 個採集批次」來源不明，不當作現行樣本統計。原文未被擷取的歷史資料不能改標為完整原文；正式 v3 訓練需要新採集、來源證據對帳與獨立批次。補同模板筆數不能取代獨立 session、家族與合法特殊字元情境，亦尚缺事前接受標準與實際服務效能驗證。

## 每次實驗保存的檔案

- model.json、metadata.json：跨系統模型、特徵版本及候選標記。
- report.md：方便閱讀的數據表與混淆矩陣。
- report.json：完整數值、比較基準、信賴區間狀態、切分統計、資料／程式 SHA-256、套件版本、參數與延遲。
- predictions.csv：逐筆真實類別、預測、機率及樣本 ID，用來找誤報與漏報。
- split.csv：每筆的集合與群組，包含因關聯到測試集而排除的資料。

report.json 會列出跨集合『相同特徵向量』數量。此基準特徵很簡化，不同請求也可能產生同一向量；這不直接等同資料洩漏，但應回查是否只是換 ID 的模板。群組交集為零只證明已記錄關聯沒有跨集合，不能替代近似模板審查。

離線實驗模式：目前生成資料可用 --mode offline 訓練並報告分類指標，結果明列 mode=offline、exploratory=true，不聲稱平台 HTTP 驗證。--mode live 仍核對真實請求證據。分數解讀應區分這兩種實驗條件。

v3實驗規則：一般test是已見家族的不同模板與API；challenge另外保留未見編碼／語境。Sylius validation使用新抽樣外部輸入，不能將三份保留集合混成一個分數。family共享只在明確的v3協定允許，模板、原文及真實session仍嚴格隔離。新舊資料／特徵同時改動，不作單因素提升歸因。
