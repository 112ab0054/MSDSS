# v2 參數補全、比例與待辦

日期：2026-11-09。主專案 Documents/GitHub/MSDSS；三份人工 API 文件、原始契約與舊資料不覆寫。

## 比例修正

v1 的 165/38/118 是覆蓋產生器自然得到的筆數，沒有先設取樣配額。比例本身沒有通用的「合格數字」，獨立平台驗證也不一定要佔固定百分比；但 v1 沒有控制類別數，不適合作為這次小規模實驗的最終安排。

v2 採 420 筆，60/20/20，並保持每個集合三類等量：

| 集合 | 平台 | normal | sqli | xss | 合計 |
|---|---|---:|---:|---:|---:|
| train | Bagisto＋Shopware | 84 | 84 | 84 | 252 |
| test | Bagisto＋Shopware | 28 | 28 | 28 | 84 |
| validation | Sylius | 28 | 28 | 28 | 84 |

Bagisto／Shopware 各留 4 個 API 操作給測試，其餘操作給訓練，操作與本地攻擊家族不跨集合。填入的歷史正常值也使用不同流程來源；來源詳見 provenance.json。常駐商品等共用資源的識別值可以相同，不能把同一流程的請求拆到兩邊冒充獨立。正式採集仍需重新建立各集合的 session。

驗證攻擊 payload 與部分正常文字來自固定 commit 的 httpParamsDataset；剩餘正常控制是 API 文件／歷史正常值導向候選。沒有 Medusa。沒有為湊數新增換尾數的 SQLi。比例與類別平衡不證明模型效果，也不取代來源／近似重複審查。

採樣單位為 140 組「正常對照＋單欄 SQLi＋單欄 XSS」，每組三筆的 Header 存在情況完全相同。可選 Header 的有無不只出現在 normal，避免模型拿缺 Header 當成正常標籤捷徑。三筆同組、不跨集合；各集合內無完全相同的請求輸入。Header、Query、Path、Body 四種變動位置在每個集合皆有候選，但不是每個欄位都有攻擊測試。

## 原 43 個物件怎麼處理

- Shopware associations 補成實體關聯對應 Criteria，例如商品 `{"media":{"limit":1}}`；includes/excludes 補成實體名稱對應欄位陣列，兩者不故意選同欄。
- filter/post-filter、sort、aggregations、fields、grouping 等陣列，分別使用原始 EqualsFilter、FieldSorting、count Aggregation、欄位名稱陣列結構，不再放 `${LIVE:...}` 字串。
- billingAddress/shippingAddress 依原始 Address required 補齊 countryId、firstName、lastName、zipcode、city、street；國家 ID 取自正常 HTTP 證據。
- items[].payload 填附加鍵值；customFields 填測試鍵值，但平台只儲存已定義的自訂欄位，尚未宣稱已建立其定義。
- Bagisto superAttribute、qty、bundleOptions、bundleOptionQty、booking 等依參數含義與本機固定核心程式填出結構。數字鍵只是結構示例，不能冒充已建立的複合商品屬性／組合／預約種子。
- Sylius 的 `（本文）` 是整個 object 本文，移除錯誤的同名 JSON 屬性。既有正常建立購物車請求為 `{}`，此處保留空物件有證據，不是尚未補內容。

這些是**形狀與候選值補全，不是 43 個結構都已實機驗證**。Bagisto 不同商品型別的選項須在正式採集時拆成相容流程，不能把完整欄位覆蓋候選整筆當成 simple 商品可接受的請求。

## 另記文件差異，原文不改

1. Shopware ProductListingFlags 的 `reduce-aggregations`、`no-aggregations`、`only-aggregations`：原始 schema 為 oneOf string/null、以存在表示的旗標，人工表曾列為 object。候選改填字串 `"1"`，其組合效果待實測。
2. Sylius POST orders 的 `（本文）` 是整體本文的描述，不是可送出的欄名。
3. Shopware countryStateId 是選填關聯，歷史測試使用德國地址並未提供有效州省 ID。本版兩個位置明確填 null 並列待測；若實例不接受 null，正式流程應省略，不得編造 UUID。

依據：三份 API_parameters.md、sentinel/analysis/api-contracts/shopware/storeapi.json 的 Associations/Criteria/Includes/Excludes/ProductListingFlags/Address、Bagisto 選定 add-product-in-cart 契約及固定核心 Product/Type/Booking.php 的 prepareForCart。規格快照與固定部署版本可能有差異，本次未覆寫任何規格或 ready_for_collection。

## 原 180 項的重新分類

620 個位置中，82 個是密碼、Authorization、購物情境 Token 等憑證，必須遮蔽，不能把明文填進公開 CSV。它們不是 82 個缺少結構的欄位。其他識別值優先取已對帳的同操作、同集合歷史正常紀錄；Sylius 分類代碼由商品 mainTaxon IRI 取得。

本版沒有 `${LIVE:...}` 佔位字串，但還有實際前置條件：

- 6 個條件商品欄位：需要建立並取得對應型別種子，現在僅結構示例，不是有效商品選項 ID。
- 1 個 customFields：需建立實例可接受的自訂欄位定義或按實例規則省略。
- 2 個 countryStateId：null 的接受方式需實機確認。
- 歷史商品、購物車、地址、訂單 ID 不代表現在仍有效，尤其結帳後購物車與登出後 Token 不能直接重用。實際重播須從當次回應重新取得。

其餘已填值也仍需格式與業務驗證，不能因不含佔位符就核准訓練。
