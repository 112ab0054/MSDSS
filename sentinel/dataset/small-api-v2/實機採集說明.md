## 真實 HTTP 採集

新增 ../collect_small_v2.py：每筆先建立新的正常流程，在同 API 的實際操作階段取得當次 ID、Token 與 Cookie，再執行候選。敏感值只在記憶體及忽略提交的本機設定中使用，證據保存時遮蔽；不使用假 Token，不把缺少動態值的請求硬送出。複合商品缺種子時明確阻擋。

只能對 msdss-phase1 的本機隔離容器執行，並檢查容器 project 與 loopback 埠。正常業務／攻擊是否成功與 HTTP 是否送出分開；全部保留 pending_human_review、training_approved=false。只因回傳 200/201，不能自動核准訓練或宣稱攻擊成功。

```sh
python sentinel/dataset/collect_small_v2.py --platform bagisto --split train --limit 3 --execute
python sentinel/dataset/collect_small_v2.py --platform shopware --split train --limit 3 --execute
python sentinel/dataset/collect_small_v2.py --platform sylius --split validation --limit 3 --execute
```

可用 --path 指定 API 模板，--label 指定類別。先做小批次檢查；省略 --limit 才是該平台／集合的全部候選。每筆都需要重建前置流程，耗時與 HTTP 數量會高於候選筆數。

輸出另存於 ../live-small-api-v2/<平台-UUID>/，原 v2 CSV 不覆寫：

- candidates.jsonl：真正送出且取得回應的目標請求。
- outcomes.json：每筆計畫是否送出、回應狀態、阻擋原因。
- HTTP 證據：../evidence/<平台-UUID>-<序號>.json。

每個 HTTP 請求限速，遇到 401/403/429 就停止該平台。限流狀態不清除、不提高額度；重新執行須遵守後端 retry_after，不能連續重跑湊筆數。失敗／未送出的請求留在 outcomes，不能算已實測樣本。原始正常候選出現非 2xx 不自動作為正常業務成功樣本。

## 已發現並修正的實機差異

- Bagisto 的舊參數表未在每個位置重列繼承認證。採集時需保留正常流程當次核發的有效 bearer，而非只複製候選表的 header。
- Shopware 候選 sw-language-id 原值不是有效 UUID，曾回傳 412。實機改從當次 /context 的 languageIdChain 取值，攻擊目標恰為該 header 時則保留攻擊值。
- Shopware 地址清單 filter/post-filter/ids 必須指向當次建立的地址，不能沿用歷史 UUID。
- 舊 Cookie 不能重播；實際 cookie 由當次 CookieJar 決定，不捏造不存在的 Cookie。
- Bagisto 已遇到 429，後端回應的等待時間可能長於名義分鐘限額；相關限制保留，不當成模型效果。

實際進度見 live-execution-status.json；沒有全數完成或人工審核前，仍不能正式訓練。
